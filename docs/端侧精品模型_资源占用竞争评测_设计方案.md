# 端侧精品模型：资源占用竞争下的时延/性能评测设计方案

> 对照需求：`docs/端侧精品模型测试指标_缺口分析与补齐方案.md` 及其基准需求文档
> 目标机：`macmini`（192.168.3.5，M5 Pro 64GB，统一内存）
> 分析日期：2026-11-26

## 1. 背景与目标

现有评测只在「独占机器」下测模型性能。真实端侧部署中，模型进程常与其它负载共享
统一内存上的 CPU / GPU / 内存 / 带宽，模型可用资源被抢占，Prefill/Decode、TTFT、
吞吐会随之退化。

本方案构造**可复现的资源占用档位**（0/10/20/30/50/60/80%），在每档稳定占用下以
**固定并发**跑评测，量化模型各项时延/性能指标随占用率的变化。

## 2. 口径约定（务必先看）

| 项 | 约定 |
| --- | --- |
| 压测维度 | **单目标资源串行**：一次只把一类资源推到目标档位；其余资源不强控为 0，其实际占用作为**副产物随动并全量记录**（见 §3.5） |
| 档位 | `--tiers 0,10,20,30,50,60,80`；`0`=基线（不压） |
| 内存档位 | **整机总占用**（含模型常驻 ~22GB ≈ 35% of 64GB）；低于基线的档位标记 `unreachable` |
| CPU 档位 | 整机 system-wide `used%` |
| GPU 档位 | GPU HW active residency |
| 带宽档位 | 对理论带宽（M5 Pro = 273GB/s，非需求文档 120GB/s）的占用比，为**校准设计目标** |
| 并发 | **保持不变**（本轮不引入并发维度） |

## 3. 四类资源构造方法

### 3.1 CPU 占用
- 机制：`multiprocessing` 忙等进程，每进程 ≈ 1 核。
- 控制：闭环 PID。每 1s 采样 `psutil.cpu_percent`（无 psutil 回退 `top -l 1`），
  `error = target − used`，增减进程数，钳制 `[0, ncores − 2]`（留 2 核给监控/评测客户端/server）。
- 收敛：连续 3 采样 `|error| ≤ 3%`。

### 3.2 内存占用
- 机制：`bytearray` 分配 `目标 used_gib − 基线 used_gib` 匿名脏内存，keeper 线程
  周期性触页保持 resident（脏/活跃）。
- 控制：闭环 PID，每 2s 读 `vm_stat` used_gib 微调。
- 保护：上限 ≤ 90% RAM；触发 swap 增量或内存压力非 normal 即下调。

### 3.3 GPU 占用（MLX matmul）
- 机制：单进程 MLX 大矩阵 `matmul` 循环，用 duty cycle（compute-burst + `time.sleep`）门控。
- 控制：开环 + 校准表。因 GPU residency 需 `sudo powermetrics` 无法在 stressor 内廉价闭环：
  离线对 duty∈[0.1…0.9] 测 `gpu_usage_percent` 得 `residency↔duty` 映射，运行时反查。
- 达成值：monitor 的 `gpu.gpu_usage_percent` 作为 ground truth。
- 保护：duty ≤ 0.9，监控 `thermal_pressure` 跨 Nominal→Moderate 即降。

### 3.4 带宽占用
- 机制：numpy 大数组流式拷贝（释放 GIL），无 numpy 退回 multiprocessing 每进程流式读写。
- 控制：开环校准。离线测「单 worker GB/s」，拟合「worker→有效 GB/s」，按
  `目标% × 理论带宽` 反推 worker 数。无硬件计数器，标注 `calibrated_open_loop`。

### 3.5 负载副产物（交叉耦合，重要）
「单目标资源」不等于「其它资源为 0」。任一 stressor 都会连带抬升其它资源，
因此 **monitor 全程对四类资源一起采样（metrics.jsonl 每 2s 一条全量快照）**，
每个单元的实际达成是一个**四维向量** `{cpu%, mem%, gpu%, bw%}`，而非只记录目标那一路。

各 stressor 的典型副产物：

| 目标资源 | 连带抬升 | 原因 |
| --- | --- | --- |
| GPU（MLX matmul） | CPU↑、内存↑ | 命令提交 + 运行时占用 CPU 核；矩阵/runtime 分配内存 |
| CPU（忙等进程） | 内存略↑ | 每进程栈/代码段；GPU 基本不动 |
| 内存（触页 keeper） | CPU↑ | 页面故障、内核回收、keeper 写页占用 CPU |
| 带宽（流式拷贝） | CPU↑、内存↑ | 向量化拷贝吃多核；缓冲区分配占用内存 |

含义：模型退化的归因必须基于**「目标档位 + 其余资源实际向量」联合刻画**，
不能假设其余资源为 0。报告里每个单元都要同时给出 CPU/内存/GPU/带宽四路达成值。

## 4. 控制与收敛流程

```
编排器(run_contention_bench)
  └─ for (resource, tier):
       start monitor_machine  ──── sudo powermetrics + 2s 采样落盘
       start resource_stressor ── 构造负载，写 status-file
       poll status-file ───────── 等 converged（超时→NOT_CONVERGED 继续）
       run bench_accuracy_concurrency（固定并发，写逐请求 stage jsonl）
       stop stressor ──────────── 精确 PID
       stop monitor
```

### 5.2 设备信息（需求 → 监控）

| 需求项 | 监控字段 | 可否构造档位 |
| --- | --- | --- |
| ① GPU/NPU 使用率 | `gpu.gpu_usage_percent` / `npu_usage_percent` | GPU 可；NPU 本轮不单压 |
| ② CPU 使用率 | `cpu.used_percent`（+ `cpu_clusters`） | 可 |
| ③ 内存（含显存） | `memory.used_gib_approx` / `free_gib` 等 | 可（整机口径） |
| ④ 算力 | `compute.effective_tflops`（推导） | 不直接构造，作观测量 |
| ⑤ 带宽 | `compute.effective_bandwidth_gb_s`（推导） | 可（构造 DRAM 吞吐） |

> 显存、实时带宽在统一内存/无用户态计数器下只能近似或推导，报告须标注架构限制。

### 5.3 核心因变量（随档位变化的观测量）

| 组 | 观测量 | 需求字段 |
| --- | --- | --- |
| Prefill/Decode | prefill 速度、decode 速度 | `prefill_tps` / `decode_tps` |
| 时间 | 首 token 延时、服务端总时长、端到端 | `first_token_time` / `server_wall_s` / `client_e2e_s` |
| 吞吐 | 输入/输出/总 token 速率、请求速率 | derived |
| 正确性 | 准确率（理论不变） | `correct` |

## 6. 产物结构

```
results/contention/<model>/
  cpu_0/    cpu_10/    cpu_20/ ... cpu_80/
    monitor/metrics.jsonl, manifest.json, charts/
    bench/stage_1.json, stage_1_requests.jsonl, manifest.json, summary.md
  memory_*/  gpu_*/  bandwidth_*/
  summary.json        # 全矩阵 {target, achieved_vector{cpu,mem,gpu,bw}, ttft, prefill_tps, decode_tps, ...}
  summary.md
```

每单元 manifest 记录：`contention_resource`、`contention_tier`、目标占用、stress 参数、
**实际达成占用四维向量（cpu/mem/gpu/bw 的均值/标准差）**、是否 converged、sudo/MLX 是否就绪。

## 7. 依赖、权限与安全

- `sudo powermetrics --samplers cpu_power,gpu_power,ane_power,thermal -i 2000`（只读采样）。
- MLX：复用机器已装环境（GPU stress）；缺失则 GPU 档 `unavailable` 跳过。
- 其余 stdlib + 可选 `psutil` / `numpy`。
- stressor/orchestrator 仅停本任务启动的 PID，遵守远端 R2 规范；sudo 需批准。

## 8. 风险与边界

| 风险 | 处理 |
| --- | --- |
| GPU residency 需 sudo 才能测 → 无法在 stressor 内闭环 | 开环 duty 校准 + monitor 记录达成值 |
| 带宽无硬件计数器 | 标注 `calibrated_open_loop`，报告用设计目标 + 模型推导带宽交叉说明 |
| 统一内存：带宽 stress 与内存/GPU 竞争物理同源 | 设计文档明确三者共享 DRAM 基板，避免把「带宽」当作独立资源误读 |
| 内存低档位低于模型基线 | 标记 unreachable 并记录原因 |
| 热降频/内存压力 | duty ≤0.9、内存 ≤90%RAM、worker 留核、监控 thermal/pressure |

## 9. 验证方式

1. `python -m compileall -q tools/`；stressor 各 kind `--dry-run`。
2. 单机小样本冒烟：CPU 50%、内存 60% 各跑 1 档，核对 status-file 收敛与 monitor 达成值。
3. 对 2~3 样本试跑，人工核对 stage jsonl 中 Prefill/Decode/时间字段与需求字段一致。
4. 产出 summary 矩阵，核对「占位档位 → 四路达成占用向量 → 模型退化」趋势合理（单调或饱和），
   并检查每个单元的非目标资源副产物是否被如实记录（如 GPU 档的 CPU/内存抬升）。
