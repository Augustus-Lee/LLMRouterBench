# 单模型性能评测耗时评估与机器独占通知

> 评测机器：`192.168.3.5` / `Jiuwen-MacMini` / Apple M5 Pro / 64GB
> 评测范围：MLX 单模型性能摸底，单请求、单并发
> 目标模型：Qwen3.6-35B-A3B-4bit、Gemma-4-26B-A4B-4bit（三个文本模型逐一执行）
> 评估日期：2026-11-23（Asia/Shanghai）

---

## 1. 对外承诺建议

| 场景 | 建议独占时间 | 说明 |
|---|---:|---|
| 仅加载/接口冒烟 | 15～30 分钟 | 验证模型可加载、OpenAI 接口可请求 |
| 快速性能摸底 | 1.5～2 小时 | 短上下文、较少重复，不做长上下文边界探测 |
| **单模型正式评测（推荐口径）** | **4 小时** | 完整短/中上下文矩阵、预热、3 次重复、内存记录、结果核验 |
| 首次执行或需要长上下文边界探测 | **6 小时** | 包含 32K/64K/128K 压力测试、异常复跑和缓冲 |
| 三个模型串行正式评测 | **12～18 小时** | 不应连续一次跑完，建议拆成 3 个独立窗口 |

**对外通知建议写“4 小时/模型”；如果是第一次跑完整流程，写“6 小时/模型”。**

原因：

- 自动推理本身通常远短于 4 小时；
- 但正式结果需要预热、重复、长上下文压力、swap 监控、异常复跑和数据核验；
- 共享机器上出现后台负载、热降频或 swap 时，必须重跑整组，不能挑选漂亮数据；
- 给同事承诺过短，会增加中途被打断、结果作废和重复占用机器的风险。

---

## 2. 为什么不是“几十分钟跑完”

当前冒烟数据：

| 模型 | 峰值内存 | 短回答 Decode 速度 |
|---|---:|---:|
| Qwen3.6-35B-A3B-4bit | 约 20.52GB | 约 91.5 token/s |
| Gemma-4-26B-A4B-4bit | 约 15.42GB | 约 84.7 token/s |

按这两个速度估算，纯 Decode：

- 生成 256 token：约 2.8～3.0 秒/请求；
- 生成 512 token：约 5.6～6.0 秒/请求。

因此如果只跑少量短请求，生成时间确实只有几分钟。真正占用窗口的是：

1. 模型加载与首次 Metal 图构建；
2. 每个场景至少 1 次预热，预热结果必须丢弃；
3. 每个场景正式重复 3 次；
4. 16K、32K、64K、128K 长上下文 Prefill；
5. 长上下文失败时的超时、进程重启和边界确认；
6. 峰值内存、RSS、swap、温度与后台负载采样；
7. 结果汇总、异常值检查和不稳定场景复跑。

## 3. 单模型 4 小时的时间拆分

以完整方案中的 S1～S5 必测场景为主：

```text
上下文：128、1K、4K、8K、16K
输出：256 token 为主，512 token 复核
重复：预热 1 次 + 正式 3 次
```

建议时间预算：

| 阶段 | 预计耗时 | 主要内容 |
|---|---:|---|
| 环境与机器状态检查 | 15～20 分钟 | 版本、磁盘、内存、swap、残留服务、后台负载 |
| 模型加载与接口验证 | 10～20 分钟 | 单次生成、服务就绪、模型 ID、Chat 请求 |
| 短/中上下文正式矩阵 | 40～70 分钟 | 128～16K，预热、3 次重复、256/512 输出 |
| 内存与稳定性采样 | 20～30 分钟 | 峰值内存、RSS、swap、系统压力、温度 |
| 长上下文边界探测 | 45～90 分钟 | 32K/64K/128K 阶梯或二分，失败点确认 |
| 异常复跑与结果核验 | 30～60 分钟 | 重跑抖动场景、校验日志和字段完整性 |
| 报告整理与机器恢复 | 20～30 分钟 | 汇总表、图表、停止服务、确认无残留 |
| **合计** | **约 3～5.5 小时** | 对外按 4 小时，首次按 6 小时 |

> 这是工程执行时间，不是单纯的 benchmark 自动运行时间。纯自动推理很可能只占其中 20～40 分钟。

## 4. 不同评测深度的时间

### 4.1 快速摸底：1.5～2 小时/模型

适合先判断模型是否能稳定运行：

- 128、1K、4K、8K；
- `max_tokens=256`；
- 预热 1 次 + 正式 2～3 次；
- 只记录 Prefill、Decode、峰值内存和 swap；
- 不做 64K/128K 边界探测。

### 4.2 标准正式评测：4 小时/模型

适合形成可写入报告、可复现的结果：

- 128、1K、4K、8K、16K；
- 256 与 512 输出；
- 预热 1 次 + 正式 3 次；
- 32K/64K 作为可选压力场景；
- 记录 MLX 峰值、进程 RSS、swap、后台负载与版本；
- 异常场景复跑。

### 4.3 扩展压力评测：6～8 小时/模型

适合研究上下文上限和热稳定性：

- 增加 32K、64K、128K；
- 增加持续 10 分钟压力；
- 多次重复与边界附近二分；
- 对比 KV Cache 量化；
- 若发生 OOM/系统卡顿，需要冷却和重启后复测。

## 5. 三个目标模型的总时间

| 执行方式 | 建议总时间 | 安排建议 |
|---|---:|---|
| 三个模型快速摸底 | 4～6 小时 | 可在一个半天内完成，但建议中途留冷却时间 |
| **三个模型正式评测** | **12～18 小时** | 拆成 3 个独立 4～6 小时窗口 |
| 加 M4/M5 对照复测 | 20～30 小时 | 每个模型在两台机器各跑一轮，另行排期 |

不要为了“省窗口”让三个模型连续满载十几小时。长时间运行会引入热降频、内存碎片和系统缓存差异，且中途失败会导致整段结果不可比。

推荐拆分为：

```text
窗口 1：Qwen3.6-35B-A3B
窗口 2：Gemma-4-26B-A4B
窗口 3：Qwen3.8-27B
```

每个窗口之间至少留 15～30 分钟，确认温度、内存、swap 和残留进程恢复正常。

## 6. 机器独占要求

评测期间建议独占以下资源：

- Apple GPU / Metal；
- 统一内存；
- 模型推理服务；
- 高负载 CPU 任务；
- 大文件下载、拷贝和视频导出。

允许保留：

- SSH 管理连接；
- 轻量终端命令；
- 必要的监控和日志采集。

不建议同时进行：

- Ollama、oMLX、EXO、Splash 等其他模型推理；
- Xcode 编译、大型 Python 构建、视频转码；
- 大模型下载或大文件同步；
- 多用户并发请求；
- 长时间高内存浏览器或 IDE 任务。

即使内存看起来足够，两个模型同时加载也会压缩 KV Cache 和系统余量，并改变内存带宽、GPU 调度和散热状态，导致性能数据不可比。

## 8. 结论

- **单模型正式评测：对外预留 4 小时。**
- **首次执行、包含长上下文边界探测：预留 6 小时。**
- **仅快速摸底：1.5～2 小时。**
- **三个模型正式评测：总计 12～18 小时，必须拆成独立窗口。**

实际自动生成耗时较短，真正需要独占的是预热、长上下文压力、重复测量、异常复跑和稳定的机器环境。
